### R3 investigation result and safe implementation boundary

The Team Room service source defines POST /auth/exchange accepting a workload token and room UUID. It validates token signature through issuer-anchored JWKS, issuer, exact audience team-room-api, time validity, JTI, and team_room:connect; then requires an active issuer+subject registration for an enabled AI principal/workload identity and an active room. JTI replay is denied. The response includes a short-lived local bearer session and server-derived principal/participant/session/execution/room/issuer/subject identifiers.

For a secure Supervisor implementation, all exchange parameters must be Supervisor-owned configuration/state; the RPC client must not select a token, subject, room, phone identity, or remote credential. The Supervisor must compare the exchange's server-derived identity to a provisioned expected issuer+subject and map that expectation to the observed local AppContainer identity before storing remote session data. Remote bearer/session material must not cross RPC. Missing, mismatched, expired or unconfigured values must fail closed.

This is an implementation design constraint, not a claimed implementation. The required real registration/configuration proof is absent, so the mission deliberately did not create code that accepts an unverified binding.

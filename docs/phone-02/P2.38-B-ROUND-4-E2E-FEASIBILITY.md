## Existing real-Keycloak evidence in repository

`.github/workflows/ci.yml` contains a `keycloak-oidc-smoke` job on `ubuntu-latest`. It starts Keycloak 26.3.5 and PostgreSQL 16 as ephemeral CI services, creates a realm and confidential service-account client, obtains a real `client_credentials` token, validates RS256/JWKS, starts the real Rust Team Room service, performs `POST /auth/exchange`, checks issuer/subject/audience/scope, verifies the opaque local session digest in PostgreSQL, checks permissions/admission, rejects replay, and scans logs for credential leakage.

This is genuine Keycloak-to-Team-Room resource-server evidence in the CI design. It does **not** exercise Windows Supervisor, MSIX/AppContainer, ncalrpc, WinHTTP token acquisition, Supervisor secret custody, endpoint credential lifecycle or the requested identity key. It uses `curl` from Ubuntu and must not be relabeled as the P2.38-B E2E.

## Existing Windows P2.38-A harness limitation

`.github/workflows/phone-02-p238-a-tls-e2e.yml` runs on `windows-2025`, but the Team Room process is explicitly started with `TEAM_ROOM_TLS_PROBE_ONLY=1`. In that mode `main.rs` serves only liveness routes and bypasses PostgreSQL migrations, OIDC configuration, identity registry, token exchange and phone API handlers. The Windows E2E therefore proves the P2.38-A TLS health path only.

The current Windows workflow does not start PostgreSQL or Keycloak, create a realm/client/service account, configure the Team Room OIDC resource server, or bootstrap the administrative identity/operator-key grants required for endpoint registration.

## Why no P2.38-B E2E was started

A Windows AppContainer/Supervisor E2E needs the following components in one controlled execution boundary:
1. Windows MSIX/AppContainer and the existing RPC Supervisor service;
2. ephemeral Keycloak realm with confidential service account and client secret;
3. ephemeral PostgreSQL with Team Room migrations and test-only tenant/room/principal/participant/workload rows;
4. Team Room full application process with HTTPS listener and exact OIDC issuer/audience configuration;
5. admin-side provisioning of `TEST-AI-PHONE-02-P238`, AI_PHONE_ID, operator-key hash and permissions;
6. Supervisor-only protected storage and WinHTTP clients for Keycloak token endpoint, Team Room token exchange and phone API routes;
7. lifecycle assertions against PostgreSQL, plus proof that AppContainer cannot read protected storage or observe remote credentials;
8. cleanup of Windows service/package/processes, Keycloak, PostgreSQL, certificates, trust material, credentials, temporary files and any ephemeral volumes.

The existing Ubuntu Keycloak job and Windows AppContainer job are separate runners. No authenticated cross-job secret transfer or shared ephemeral network/database exists. Reusing the Ubuntu job output by publishing tokens or secrets as artifacts/job outputs would violate the custody requirement. The current Windows workflow has no local Keycloak/PostgreSQL bootstrap.

## Required acceptance sequence for a future live run

The test must collect independently verifiable server-side evidence for:
- Keycloak discovery issuer and token endpoint; real service-account subject, exact audience and `team_room:connect` scope;
- real token acquisition; successful Team Room exchange; local session issuer/subject/principal binding; expiration and invalid/expired assertion rejection;
- protected-store ACL and read-denial checks from AppContainer/common user; no remote secret/token in RPC IDL, client memory, logs, crash output or artifacts;
- server-admin identity creation and exact Keycloak subject binding for `TEST-AI-PHONE-02-P238`; nonexistent and divergent mappings rejected;
- one-time endpoint credential registration, hash-only DB storage, attach fence, heartbeat, reconnect with higher fence, detach, revoke, rotation and rejection of old/revoked/expired credential;
- cleanup marker plus independent post-cleanup checks for Keycloak/PostgreSQL processes, database/container/volume, Windows certificate stores, service, MSIX, secret store entries and temp directory.

The E2E must use the real AppContainer to call only the existing RPC operation; no RPC method may accept token, client secret, operator key, endpoint credential, CA/private key, AI_ID or AI_PHONE_ID. The Supervisor must derive the phone identity from its protected server-provisioned binding and server response.

## R1 — Operational checklist and evidence contract

### A. PHONE-02 REAL — target Windows device

1. Identify the exact physical/VM host that is designated Phone-02. Record an operator-controlled host inventory reference and Windows build. Do not send serial numbers, account names, device secrets, or other unnecessary identifiers.
2. Obtain the exact signed Phone-02 application package from its authorized build/release process. Verify publisher/signature and package provenance locally. The repository evidence inspected for this checkpoint does not identify a release artifact or a validated install command; an authorized release/operator must supply those before installation can be considered reproducible.
3. Install and launch that exact package under the intended Windows user/session. The process must actually run as an AppContainer. Do not substitute a CI runner, a command-line mock, a service account, or a different package.
4. Run the existing Supervisor RPC identity observation by invoking the normal local RPC session flow from that packaged process. The server-side `ObserveCaller` path obtains the caller PID and local RPC attributes, impersonates the RPC caller, and reads `TokenIsAppContainer`, `TokenSessionId`, `TokenUser`, `TokenAppContainerSid`, package family, package full name, and process creation time. It reverts impersonation before continuing and compares the observed values with configured pins.
5. The expected `USER_SID`, `APPCONTAINER_SID`, `PACKAGE_FAMILY`, and `PACKAGE_FULL` pins must be derived from the actual signed package and actual target-device runtime token by an authorized local administrator. The repository contains pin-loading/verification logic, but this audit did not find a target-device enrollment tool or a documented admin command that safely derives and writes these values. Do not hand-edit guessed values into configuration.
6. Capture a sanitized evidence bundle locally. It must contain: package publisher/signature verification result; package family and full name; AppContainer SID; user SID (redact user/account name); Windows session ID; process image/package provenance; Supervisor build SHA; and the Supervisor's `RPC_OBSERVED ... result=IDENTITY_MATCH` line. Preserve the exact SID/package values in the admin-controlled evidence channel because they are identifiers needed for exact comparison; redact unrelated user/device identifiers. Do not include access tokens, client secrets, passwords, private keys, cookies, or bearer strings.
7. If the runtime does not produce `IDENTITY_MATCH`, or the token is not an AppContainer, stop. A config file containing expected values is not proof. A CI AppContainer artifact is not proof of the physical Phone-02 identity.

**R1-A acceptance:** the exact signed package provenance and OS-observed runtime identity match are both present, and the expected pins were provisioned by an authorized administrator from that same target package/runtime. Current status: **BLOCKED — no target-device evidence or supported pin-enrollment procedure**.

### B. OIDC PROVIDER — trusted workload identity

1. The OIDC administrator must select an issuer and a workload-federation method that can authenticate the actual Phone-02 runtime identity. The issuer must not accept a caller-selected subject, a model name, a display name, a static shared secret alone, or a CI service-account identity as Phone-02 proof.
2. Establish the exact HTTPS issuer URL and its discovery metadata. The service must use the exact configured issuer and its issuer-anchored JWKS; no token-supplied issuer/JWKS URL is trusted.
3. Provision a dedicated Phone-02 workload subject using the approved federation mechanism. Record the exact `sub` from an actual short-lived assertion produced by that mechanism. The administrator must retain the provenance linking the assertion to the target Phone-02 identity. Do not send the JWT/assertion itself.
4. Configure exact API audience `team-room-api`, required scope `team_room:connect`, and RS256 signing with a published RSA JWKS key and `kid`. Ensure the access token contains `iss`, `sub`, `aud`, `exp`, `iat`, `jti`, and the required scope. Keep the assertion short-lived and single-use.
5. Provide only sanitized provider metadata: exact HTTPS issuer, exact subject, audience, scope, signing algorithm, JWKS URL, key ID, assertion issue/expiry timestamps (not token contents), and an administrator-signed or otherwise auditable record of the federation binding. Never provide a client secret, private key, access token, ID token, JWT, refresh token, or raw HTTP authorization header.
6. Do not use the repository's local Keycloak client-credentials example as proof of Phone-02 identity. The existing R5 client-secret/DPAPI-NG flow proves credential possession to an issuer; it does not attest the Windows AppContainer. If the selected provider cannot bind a workload assertion to the target runtime identity, stop and mark the identity federation unsupported.

**R1-B acceptance:** the Phone-02-specific workload federation is documented and testable, exact issuer/subject are known from the real federation path, and an auditable administrator record binds them to the target package identity. Current status: **BLOCKED — no approved federation provider/method or Phone-02 subject provisioned**.

### Exact binding gap

The existing pieces are separate trust domains and no server-side or Supervisor-side association currently joins them:

`OS-observed Phone-02 package/AppContainer identity`
→ **MISSING TRUSTED FEDERATION LINK**
→ `OIDC issuer + subject`
→ **MISSING PHONE-02 ACTIVE REGISTRATION**
→ `AI principal + participant`
→ **MISSING PERSISTENT PHONE-02 ROOM + room.join**
→ **MISSING SUPERVISOR /auth/exchange AND RESPONSE-BINDING CODE**

The OIDC server validates the token and performs the issuer+subject lookup, but it cannot independently infer that the token originated from the Windows AppContainer. The Supervisor has local identity proof but currently does not perform the exchange. An administrator-approved, cryptographically enforceable federation link must bridge those facts before binding code can be safe.

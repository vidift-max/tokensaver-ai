# P2.37 — Controlled Supervisor ↔ Team Room bridge contract

Status: isolated Windows test contract. No production activation, live Team Room URL, real OIDC assertion, real session token, real endpoint credential, Phone-01 traffic, merge or deploy.

## Identity namespaces — never interchangeable

| Namespace | Authority | Purpose |
|---|---|---|
| Windows PID + process creation time | Windows kernel, observed by Supervisor during RPC impersonation | Ephemeral process instance |
| Windows token User SID + Windows session ID | Windows access token | Local logon identity |
| AppContainer SID + package family/full name + publisher | Windows package/token APIs; pinned by privileged test harness | Packaged client identity |
| AI_PHONE_ID | Team Room phone registry; created by privileged provisioning | Tenant-scoped logical phone identity |
| AI_ID | Team Room identity registry | Logical AI identity, distinct from phone |
| principal_id | Team Room OIDC subject mapping/database | Authenticated Team Room principal |
| session_id | Team Room session issuer; local Supervisor RPC session separately namespaced | Authenticated session, not a phone or process identity |
| execution_id | Team Room workload execution registry | One execution lifecycle, not an identity |

The AppContainer sends only the local RPC correlation and session selector. The Supervisor re-observes Windows identity for every bridge call and validates the session against that observed process/package binding. It does not accept identity claims from RPC arguments.

## Existing Team Room API — reuse, do not duplicate

The service router already exposes POST /auth/exchange and GET /auth/me; POST /ai-phone/identities and /ai-phone/provision; POST /ai-phone/endpoints/register; POST /ai-phone/attach, /heartbeat, /reconnect and /detach; message send, receive and ACK routes; and directional /ai-phone/pair/grant and /ai-phone/pair/revoke.

The API authenticates via the Team Room session bearer. Endpoint lifecycle and inbox operations additionally require the endpoint credential and current endpoint fence. Endpoint registration requires a separately scoped operator key and permission. Pair grants are directional and server-side.

## Trustworthy AI_PHONE_ID association

The phone identity is generated by Team Room provisioning from a privileged principal/AI identity association. The client cannot choose its own sender AI_PHONE_ID. For P2.37 Windows tests, the Supervisor reads a fixed TEST-only installation binding from the service's administrator-written configuration and combines it with Windows-observed package family, package full name and AppContainer SID. This is a test fixture, not a production phone registration.

Production still needs a privileged signed installation/provisioning record binding package publisher + package family/full name + AppContainer SID + install generation to the externally provisioned AI_PHONE_ID. No production record is created here.

## Credential custody

| Credential | Intended custodian | AppContainer exposure |
|---|---|---|
| Upstream workload assertion | Supervisor secure runtime / future federation broker | Never |
| Team Room opaque session bearer | Supervisor secret store/runtime | Never |
| Endpoint credential | Supervisor secret store/runtime | Never |
| Operator key | Separate administrative provisioning plane | Never |
| Local RPC nonce | One-use local RPC exchange; hash retained by service | Only the one-use nonce needed for local authorization |

P2.37 uses only fixed fake assertion/session/endpoint credential values inside the in-memory adapter. They are not network credentials and are never returned over RPC. The adapter has no socket, HTTP, filesystem or credential-store implementation.

## Sender identity

The sender is derived server-side from the authenticated Team Room principal by resolving its registered AI_PHONE_ID. The message response includes sender_ai_phone_id derived from the phone/principal tables; it is not accepted in a message request. Pair authorization checks sender AI_PHONE_ID → recipient AI_PHONE_ID directionally.

## RPC ↔ adapter test contract

The existing P2.36 RPC contract retains BeginSession, Authorize, Heartbeat and CloseSession. P2.37 adds the versioned RPC v1.1 method TeamRoomScenario(binding, correlation_id, session_id, status). The original P2.36 v1.0 interface is not silently extended; the test uses the distinct endpoint TokenSaver.Phone02.Supervisor.v1.1. The call contains no AI_PHONE_ID, principal_id, execution_id, token, credential, secret or sender identity.

The Supervisor re-observes the caller token and validates the authorized local session before invoking the fake adapter. The test scenario exercises authentication failure, valid fake authentication, wrong installation identity rejection, attach, distinct fake Team Room session_id and execution_id (neither equals the local RPC session or AI_PHONE_ID), endpoint ID/fence, heartbeat, reconnect, pair-grant denial then allow, send with server-owned sender identity, receive, ACK, detach, post-detach heartbeat rejection, revoke and private credential custody.

## Explicit limits

This proves only the local Windows AppContainer → ncalrpc → Windows Service → in-memory fake adapter bridge. It does not prove a real HTTPS adapter, TLS, OIDC exchange, Team Room database mutation, actual endpoint credential rotation, real pair grant creation, Phone-01 delivery or provider execution. Those remain gated.

No real credentials are used. The Windows workflow must prove the complete fake scenario and cleanup before this mission can be PASS.

## Identity model

The real Team Room identity exchange maps an OIDC subject by exact `issuer + subject` to an enabled AI principal, participant and ACTIVE workload identity. It does not trust a display name or a client-provided AI_PHONE_ID.

The phone identity API provides a separate privileged server-side operation:
- `POST /ai-phone/identities` calls `provision_ai_identity`;
- caller must hold `ai.identity.provision`;
- target principal must already exist, be enabled, and have `principal_kind='AI'`;
- tenant is required to equal the authenticated caller's tenant;
- `identity_key` is unique and is bound to the target principal;
- `POST /ai-phone/provision` requires `phone.provision` and creates the tenant-scoped AI_PHONE_ID from that binding.

For this mission, `TEST-AI-PHONE-02-P238` must be created by the test administrative principal/control-plane flow and bound to the exact principal whose issuer+subject is the Keycloak test service account. The Supervisor must receive only a server-derived binding result; the AppContainer must not choose the identity key, principal UUID, AI_ID or AI_PHONE_ID. No such identity has been created in this round.

## Sender identity

The phone messaging implementation resolves the sender phone from the authenticated principal using `ai_identity_principals` and `ai_phones`. The request's claimed `sender_ai_phone_id` is not used as authority. The existing `phone_02_postgres.rs` integration test contains explicit assertions that a forged sender field is ignored and the sender AI_PHONE_ID is derived from the authenticated principal.

This is a backend implementation/test fixture, not a P2.38-B live Keycloak-to-Supervisor proof.

## Endpoint credential lifecycle already implemented server-side

- `POST /ai-phone/endpoints/register`: requires authenticated Team Room session, `phone.attach`, and separately provisioned operator key plus `phone.endpoint.manage`. Generates a 256-bit random credential, returns it once with no-store headers, and stores only SHA-256 digest.
- `POST /ai-phone/attach`: requires the registered endpoint credential and binds it to the next monotonic endpoint fence.
- `POST /ai-phone/heartbeat`: requires current credential, active session/execution and exact current fence.
- `POST /ai-phone/reconnect`: reuses attach validation and advances fencing on a new generation.
- `POST /ai-phone/detach`: atomically detaches, increments fence and lifecycle trigger revokes credential.
- `POST /ai-phone/endpoints/{endpoint_id}/revoke`: operator-only, fences an active attachment and revokes endpoint credentials.
- Re-registering an active endpoint rotates the credential under the phone row lock; previous credential is revoked before the new one is made active.
- SQL lifecycle trigger revokes active credentials when endpoint status changes to DETACHED or REVOKED.

The existing `phone_02_postgres.rs` suite contains adversarial scenarios for hash-only storage, cross-phone credential rejection, old-credential rejection after rotation, expired credential rejection, fencing, detach, reconnect, concurrent transfer/revoke and revoked-credential rejection. These tests do not prove that the Windows Supervisor currently possesses or uses a live credential.

2. Supervisor has no API implementation to register endpoint and retain the one-time credential.
3. Supervisor has no live attach/heartbeat/reconnect/detach/revoke HTTP calls.
4. Supervisor has no server-derived identity lookup/provisioning flow for the exact identity key `TEST-AI-PHONE-02-P238`.
5. No live Keycloak realm/service account is provisioned and no external token has been acquired in this mission.
6. No test evidence yet binds the Keycloak subject to the new test identity and proves nonexistent/divergent subject rejection through the actual Windows caller path.
